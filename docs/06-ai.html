AI — Game and Workflow

Two different things share this page because they share a principle: an agent should be given a goal and a budget, not a script. First, the opponent AI that plays the game. Second, how the Claude agents building this project must behave.

Part 1 — The opponent AI

Three layers, and why three

The recurring finding in RTS AI literature is that the difficulty is not unit behaviour — it is that one system has to simultaneously watch a large map, manage many units of different kinds, and hold a long-term strategy that updates during play. Trying to do all three in one structure is what produces AI that either macros well and fights stupidly, or micros well and never builds anything. So: three layers, each with one job and a clean interface to the next.

LayerTechniqueTick rateDecidesOutput
1 · CommanderUtility AIevery 2 sStrategy: expand, tech, army, defend, attackA weighted list of Goals
2 · OfficerBehaviour trees, one per goalevery 0.5 sHow to achieve a goal: which base, which squad, which targetOrders to groups
3 · UnitSmall state machine + steeringevery frameMove, fire, flee, reload, holdMotion and animation

Layer 1 — the Commander is a utility system

Utility AI scores every possible action with a formula and picks the best (or samples from the top by weight). It is the right tool here specifically because the literature is consistent that utility systems suit resource management and strategy — which is exactly what layer 1 does — while behaviour trees suit ordered, conditional sequences, which is exactly what layer 2 does.

The commander scores ~12 goals each tick. A sketch of the real thing:

score(EXPAND)     = unclaimed_nodes_nearby × 0.8
                  × saturation(current_nodes)        // 1.0 when workers are idle
                  × (1 - threat_level)               // don't expand under attack

score(TECH_AGE)   = (knowledge / age_cost)           // 0..1, how close we are
                  × economy_health
                  × (1 + 0.6 × enemy_is_ahead)       // urgency if behind

score(BUILD_ARMY) = threat_level × 1.2
                  + (army_ratio < 0.8 ? 0.5 : 0)     // we are outnumbered
                  + opportunity(enemy_army_away)

score(ATTACK)     = army_ratio_advantage
                  × scouted_weakness
                  × (1 - our_base_threat)
                  × commitment_hysteresis            // see below
The two details that make utility AI feel intelligent instead of twitchy Hysteresis — once a goal is chosen it gets a +0.25 bonus for the next 20 seconds, so the AI commits instead of oscillating between attack and defend every two seconds. Weighted random over the top three rather than strict argmax, so the same opening does not appear in every match. Without these two, a correct utility system still plays like a malfunctioning appliance.

Layer 2 — Officers are behaviour trees

One tree per goal type, instantiated per squad or per base. Behaviour trees are chosen here for the reason they became standard: sequences, selectors and decorators are a natural, modular, readable way to express “do this, then that, unless this” — and they are easy for a designer to edit without touching the scoring maths.

ATTACK_GOAL
└── Selector
    ├── Sequence  [retreat]
    │   ├── Condition: squad_strength < 35%
    │   ├── Action: find_nearest_safe_point
    │   └── Action: move_formation
    ├── Sequence  [engage]
    │   ├── Condition: enemy_in_range
    │   ├── Action: pick_targets_by_counter_table
    │   └── Action: attack_move
    └── Sequence  [approach]
        ├── Action: request_flow_field(target)
        └── Action: move_formation

Layer 3 — Units are dumb on purpose

A unit knows five states: Idle · Moving · Attacking · Fleeing · Working. It never pathfinds for itself and it never chooses a strategic target. It follows the flow field it was given and shoots whatever the officer marked. This is what keeps 200 units cheap.

Movement: flow fields, not 200 A* queries

A flow field is a grid where every cell stores a direction vector pointing along the cheapest route to the destination, avoiding static obstacles. One field is computed per destination and shared by every unit heading there — so moving 60 units costs one pathfinding solve instead of sixty. This is the standard answer for large groups, and A* — even with jump point search — is the wrong shape here because its cost scales with the number of agents.

SituationUseWhy
Group move order (>4 units)Flow fieldOne solve, shared by all
Single unit, e.g. a citizen to a treeA*A whole field is wasteful for one agent
Local avoidance between unitsSteering / RVO on topThe field handles terrain; steering handles each other
Formation shapeSlot offsets around an anchorSee below
Formations — the one design decision worth copying exactly Keep the layout independent from the movement. The formation system generates local slots around a moving anchor and hands each unit a slot in world space. A unit must never know whether its target came from a grid, a wedge or a ring — it just walks to a point. That separation is what makes it possible to add a new formation later without touching a single line of unit code.

Difficulty without cheating

The temptation is to give the AI resource multipliers. It is the wrong lever: it produces an opponent that is not harder to outplay, only harder to out-produce, and players can feel it immediately.

LevelReaction delayMap knowledgeMicroResource bonus
Easy4.0 sFog respected; scouts rarelyNone — units attack-move only×1.0
Normal2.0 sFog respected; scouts on a scheduleFocus fire×1.0
Hard0.8 sFog respected; scouts reactivelyFocus fire + retreat wounded×1.0
Brutal0.3 sFog respected; near-perfect scoutingFull: kiting, counter-swaps, raids×1.15

Fog of war is respected at every level including Brutal. An AI that sees through fog cannot be outwitted, only out-statted, and every feint the player attempts silently fails. The 15% economy bonus appears only at Brutal, and is declared in the UI.

What the AI must never do

  • Never read the player's unit list directly. It reads its own belief of the map, updated by scouting, with stale entries decaying after 45 s. This single constraint is what makes feints, hidden expansions and surprise tech work at all.
  • Never idle its citizens. An idle-worker check every 2 s, because the most common way a competent-looking AI reveals itself as broken is eight builders standing in a field.
  • Never attack in a trickle. Squads gather at a rally point and move as one. Units arriving one at a time into a defended base is the single worst-looking AI behaviour in the genre.

Part 2 — How the Claude agents on this project must behave

This project is built largely by dispatched agents. These rules exist because the alternative has already been paid for, repeatedly, in the studio log.

Before doing anything

  1. Read PROGRESS.md. It is the state of the world.
  2. Read the design doc for the area you are touching. If your task contradicts it, say so and stop — do not silently do the sensible thing.
  3. For Blender work: load the blender-procedural and procedural-map-assembly skills, and read ~/blender/CLAUDE.md.

While working

  • One agent, one asset or one system. Agents that are given “build the Feudal age” produce eight mediocre models. Agents given “build the keep” produce one good one.
  • Never hand-edit a generated artifact. Not .blend files, not generated Unity scenes. Change the generator. This has silently destroyed work before.
  • Look at the render. A build that completes is not a build that is correct. Asset agents must open the image.
  • Two tables of the same fact is one table too many. When a material palette, a cost or a stat exists in both Python and C#, they will diverge, and the divergence will be found late.

When reporting back

The rule that cost the most to learn A measurement rounded past the thing you are measuring is not evidence. A log reading bounds (0.00, 0.00, 0.00) was read as “empty mesh” and used to reverse a correct fix; it was a 3 mm mesh printed at two decimals. Print enough precision to distinguish the hypotheses, and include a count alongside any dimension. Report what you actually verified, not what the command's exit code implies.
  • State what was built, what was verified, and what was not checked.
  • Update your row in PROGRESS.md before finishing. An agent that does good work and leaves no trace has, from the next session's point of view, done nothing.
