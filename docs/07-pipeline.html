Blender → Unity Pipeline

This is the document that saves the most time, because every trap in it has already been fallen into once on the Norse RTS and Vale projects. Read it before exporting anything.

The central fact Procedural Blender materials cannot be exported. Not to FBX, not to glTF. They arrive in Unity untextured grey. Every one of our assets is procedurally shaded. Therefore there is no such thing as “just export the model” — there are three real strategies and you must pick one per asset class, on purpose.

The three strategies

StrategyWhat crossesCostUse for
A · BakeMesh + baked albedo/normal/roughness texturesUV unwrap + bake time per asset; texture memoryTerrain, and any surface whose material is hand-painted into the mesh
B · Rebuild in engineMesh only; material re-authored as a Unity shaderWriting the shader twice, in two languagesBuildings and units — the palette is simple, flat colour + roughness per material slot
C · Sprite renderNothing. Offline Cycles renders as 2D sprites.Loses 3D entirely — fixed camera, fixed anglesNot this project. It was correct for the mobile Norse build; a PC RTS needs a rotating camera.

The decision for Clash of Ages

B for everything that moves or is built; A for the terrain.

  • Buildings and units → strategy B. Export mesh via FBX with material slots intact and names preserved. A single Unity URP shader plus a palette ScriptableObject maps material name → colour, roughness, metallic. This preserves the 3D camera the genre requires and costs one lookup table.
  • Terrain → strategy A. The terrain material reads a biome vertex attribute that encodes the hand-authored biome blend and the trodden paths. That is a painted map, and a painted map is exactly what a texture is for. Bake at 2.5 cm per texel to a 4K sheet.
Why baking the terrain is not a contradiction The rule “ground material belongs in the engine” is about materials that respond to geometry — those get frozen wrong the moment the shape changes. This one responds to an attribute authored into the mesh. It cannot be frozen wrong, because the thing it reads does not change either. Different case, different answer.

The material palette — one table, not two

This has already bitten On the Vale port, seven Norse materials arrived unmapped — Timber, BeamWood, Shingle, Stone and others — because the C# palette was written for a different kit while the Python importer's table had them. Two tables of the same fact is one table too many. Fix for this project: the palette is exported from lib/materials.py to JSON as a build step, and Unity reads that JSON. There is one authority and it is the Python. 
# blender/scripts/export_palette.py  — run whenever materials.py changes
# emits unity/Assets/Resources/palette.json
{
  "Timber":    { "albedo": [0.42, 0.28, 0.17], "rough": 0.78, "metal": 0.0 },
  "Shingle":   { "albedo": [0.24, 0.21, 0.19], "rough": 0.85, "metal": 0.0 },
  "IronDark":  { "albedo": [0.18, 0.18, 0.20], "rough": 0.45, "metal": 0.9 }
}

Unity's importer fails loudly on an unmapped material name — a magenta material and a console error, never a silent grey. The only reason the Vale bug was ever found is that the import printed what it could not map.

Tone correction

Every colour crossing to Unity is raised by pow(v, 0.62), because these palettes are authored for Cycles with the AgX view transform and Unity is not applying it. Apply it to every surface or to none. On Vale it was applied to the buildings and not the baked ground, and the result was bright orange timber sitting on pale exhausted grass.

Scale — the 3 mm grass problem

Read this before touching a MeshFilter Blender writes FBX in centimetres. Unity compensates with 0.01 on the mesh and 100 on the prefab root — the two cancel, but only if you instantiate the prefab. Lifting sharedMesh onto a bare GameObject to avoid thousands of prefab connections throws the 100 away, and everything arrives 1/100th size.

And do not then compound it with lossyScale — lossyScale on the MeshFilter already is the whole chain from the root down. Applying both counts it twice: 10,000×, and grass 236 metres tall.

Rule: set FBX import scale explicitly, instantiate prefabs for anything you did not author the transform of, and when instancing raw meshes, apply the root scale once, from the prefab asset, not from the instance.

The pipeline, end to end

1. AUTHOR      blender/base/<family>/build.py          → models/<asset>.blend
2. REVIEW      scripts/render.py (preview) → LOOK AT IT → final render
3. PALETTE     scripts/export_palette.py               → unity/Assets/Resources/palette.json
4. EXPORT      scripts/export_assets.py                → unity/Assets/Models/<asset>.fbx
                 · mesh only, material slots named, +Y up, metres
                 · asserts object count, fails loudly
5. TERRAIN     scripts/export_map.py                   → terrain.fbx + terrain_albedo.png (4K)
                 + cover.json  (instanced ground-cover transforms)
6. IMPORT      Unity AssetPostprocessor
                 · applies palette.json to material slots
                 · applies pow(v,0.62) tone correction
                 · magenta + console error on any unmapped name
7. ASSEMBLE    MapBuilder (editor script) builds the scene from the manifest
8. BUILD       Builder.PerformWindowsBuild / PerformMacBuild

Six traps found building it

TrapSymptomFix
Camera.Render() under an SRPCorrect geometry and shadows, materials silently ignored — everything flat greyRenderPipeline.SubmitRenderRequest with a SingleCameraRequest
SRP Batcher during a scripted captureCapture comes out dark and flatDisable it around the capture; leave it on for the player
-batchmodeEvery draw uses one material. A red control quad turned the whole scene red.Run the Editor in GUI mode for any visual check
Resources.Load in an AssetPostprocessorFBX imported before palette.json existed → null → every material magentaImport order is not guaranteed. Read generated data with File.ReadAllText.
FBX material remap in the .metaOnAssignMaterialModel never fires again; materials from a failed import stay wrong foreverGetExternalObjectMap() + RemoveRemap() before reimport
Objects unlinked from the scene in an asset .blendselect_set throws or reports nothing; modifiers are never evaluatedLink into the scene collection first, then apply modifiers, then count
The method lesson, which is worth more than any of the six The render was flat grey and the obvious conclusion was “the materials are broken”. They were not — reading the material assets directly gave correct colours the whole time. Adding a pure red control quad settled it in one run: red rendered grey too, so the fault was the capture path, not the palette. When a measurement disagrees with the thing it measures, add a control before you change the thing.
